# 双模型审查标准与反过度防御准则

## 1. 为什么要“宿主写 + 本地 Codex 只读审”？

| 维度 | 宿主模型（如 `gemini-4-carbon` High） | 审查模型（本地 Codex 默认配置，如 `gpt-6.2-astra` `xhigh`） |
| :--- | :--- | :--- |
| **优势** | 宏观结构清晰、改动直接干脆、多文件联动实现快、代码清爽 | 深层分支推演强、极其擅长抓状态机死角、并发竞态、契约不一致与隐式边界漏洞 |
| **常见短板** | 偶发遗漏极端边界条件、跨文件字段漏改、错误处理或生命周期收尾缺口 | 直接下场写代码时容易堆砌层层判空、防御性深拷贝、冗余包装函数与静默兜底逻辑 |
| **最佳分工** | **掌握代码编辑权**：负责出精简方案、执行 TODO、用最小改动修根因 | **严格只读沙箱（`-s read-only`）**：只交结构化缺陷证据，不直接碰工作区文件 |

## 2. 必审高价值缺陷清单（重点补齐代码与方案盲区）

### 方案阶段（`plan`）
- `architecture_flaw`：模块职责重叠、状态单一数据源（SSOT）缺失、同一逻辑多处重复实现。
- `contract_conflict`：方案假设的函数签名、表结构、配置项、文件路径与当前仓库真实源码不符。
- `missing_requirement`：遗漏用户明确提出的功能约束或关键交互路径。
- `edge_case_gap`：并发读写、中断恢复、Windows 路径/编码/无窗口进程约束（`CREATE_NO_WINDOW` / `windowsHide`）未考虑。
- `over_engineering_risk`：方案本身引入了无必要的抽象层、兼容垫片或过度防御设计。
- `verification_gap`：缺少真实可执行的验收方式（仅靠 Mock 自娱自乐而未覆盖真实入口）。

### 代码阶段（`code`）
- `missing_requirement`：对照定稿 TODO 计划存在漏实现、半成品桩代码或缩水行为。
- `bug` / `logic_edge_case`：条件反转、Off-by-one、空输入/零值在真实外部边界崩溃、编码或换行符处理错误。
- `concurrency_lifecycle`：锁竞争、异步任务未回收、超时缺失、文件句柄/临时资源泄漏、后台拉起进程触发终端弹窗。
- `contract_mismatch`：修改了数据结构/返回值/CLI 参数，但未同步更新所有调用方、序列化层或测试。
- `security`：命令参数注入、目录穿越（未限制在基准目录内）、敏感凭据写入日志或产物。
- `over_defensive_bloat`：上一轮修复或实现中混入了无意义的层层判空、吞异常 `except Exception: pass` 或死分支，需精简。
- `test_gap`：关键新增逻辑或修补过的漏洞缺少有效断言覆盖，或断言恒真。

## 3. 反过度防御红线（宿主修复时同样遵守）

以下内容**不属于缺陷**，审查端已分流至 `suppressed_over_defensive_notes`，宿主在修复其他问题时也**严禁顺手添加**：

1. **内部信任链重复校验**：私有函数或内部模块间，上游类型和调用点已保证非空/类型正确时，禁止再加 `if x is None`、`isinstance` 防御分支。
2. **吞错式防御兜底**：禁止为了“不报错”而捕获异常后返回假空值（如 `{}`、`""`、`0`），导致真实故障被静默掩盖；仅在明确的外部 I/O、用户输入或网络/子进程边界做有意义的错误处理。
3. **假想未来需求的扩展层**：禁止为当前不存在的第二种实现提前抽接口、加注册表或配置开关。
