# 原生持续执行

在需要启动、接续或管理长时间执行时读取。宿主决定运行生命周期；执行协议不模拟这些能力。

## 能力选择

| 当前情况 | 行为 |
|---|---|
| 已有与用户目标一致的原生 goal | 沿用当前目标和预算，持续执行并留下工程记录 |
| 用户要求创建或启动目标，且宿主提供相应工具 | 按工具约定建立目标；不要额外要求用户重复确认已授权的动作 |
| 宿主只提供交互式 `/goal` 入口 | 在需要时给出准确入口；能在当前会话推进的工作继续做，不假装已经启用自动续跑 |
| 当前环境没有原生持续执行能力 | 在当前会话完成可做的工作并留下交接，明确自动续跑尚未启用 |
| 用户只是在讨论方案、评价 skill 或询问状态 | 回答问题或读取状态，不启动目标或后台进程 |

先用当前可用工具及宿主文档判断能力，不因为某产品的其他版本支持功能就假设当前入口支持。slash 命令是宿主交互，不作为终端 shell 命令执行。

## 宿主适配

- **Codex**：优先使用当前会话暴露的 goal 工具或原生 `/goal`。只有用户明确要求设置目标时才创建；已有目标可用时不重复创建。预算仅按用户明确要求设置。暂停、恢复、阻塞和完成遵循当前工具的约束。
- **Claude Code**：使用当前版本提供的 `/goal` 管理有完成条件的持续任务。周期性检查才考虑 `/loop` 或 `/schedule`，且只在用户要求周期执行时使用；一次持续开发不需要额外定时器。
- **其他宿主**：选择实际存在且授权的等价能力。没有等价能力就说明边界，不编造命令，也不自动安装守护进程。

skill 的完成标准仍需落实到项目证据。宿主的完成评估不能替代实际运行测试或操作程序。

## 控制与接续

- 用户要求状态时，报告实际目标状态、已验证结果、当前切片和主要缺口，继续原任务，除非用户要求停止。
- 用户修改目标或约束时同步计划，重评受影响的验收；不要把中途问题误当取消原任务。
- 用户暂停或停止时，先服从宿主停止机制，在允许的范围内保存已知状态，不再开始新的实质工作。
- 到达预算或宿主限额时留下下一步，不能自行扩大预算、绕过限制或另起会话继续消耗。
- 新会话、压缩上下文或跨宿主接手时读取工程记录并核对实际文件。原生目标属于原会话，不能假设已经自动迁移。

## 旧控制器接手

2.0 不再运行 `scripts/harness_run_ctl.py`。如果发现旧运行记录，先确认是否仍有真实执行者修改同一工作区。通过可靠的进程身份或原运行入口确认，不能只相信历史 PID。

有正在运行的旧任务时避免并发编辑；使用可用的旧停止入口和已有授权协调交接。读取旧运行目录内的 `docs/run-plan.md`、`docs/handoff.md`、日志和源码，将有效事实纳入现有项目记录。不要清空旧证据、依照过期 JSON 直接标记完成，或自动重启旧循环。
