# 测试体系与真实操作验收

在设计验证、补齐测试或准备完成验收时读取。按目标风险选取足够的证据，避免为了“有测试”建设无关框架。

## 建立反馈能力

先检查现有测试入口、构建流程、样例数据、运行依赖和可用控制工具：

- 有成熟测试框架时沿用它，先跑相关基线，区分既有失败与本次引入的问题。
- 没有测试时，先建立最小可运行的行为检查或冒烟测试，使核心路径可重复验证，再补目标需要的边界与回归。
- 测试设施建设要服务于具体实施切片。不能把所有时间花在搭架子，或把“测试体系已搭建”当成产品目标完成。
- 根据触及的行为选择单元、集成、契约、端到端、性能或兼容性检查，不默认要求每个项目具备全部层次。
- 保留可复现入口、必要夹具和清理方式；使用项目正常的测试目录及命令。

将关键目标对应到证据。例如：

| 行为要求 | 合适的证据 |
|---|---|
| 金额、坐标、几何或转换计算正确 | 独立预期值、边界用例、容差依据 |
| 文件能往返导入导出 | 格式检查、内容比较、目标程序重新打开 |
| 服务间调用可靠 | 集成或契约测试、失败响应与重试行为 |
| 用户能完成交互流程 | 实际操作、可见反馈、保存结果及相关日志 |
| 性能或稳定性达标 | 固定场景和环境下的基线与改动后测量 |

## 防止测试自证

- 从用户要求、公开契约、可信样例、已有兼容行为或独立计算推导预期结果；不要调用被测实现来生成它自己的 expected 值。
- 修复缺陷时，能复现则先证明回归检查能暴露旧问题，再确认修复后通过。无法重现旧版时，说明证据限制。
- 覆盖关键正常路径和高价值的错误/边界路径。测试数量、覆盖率和一片绿色都不能独立证明目标完成。
- 验收标准不得为了当前实现而降低；确需纠正错误测试时记录依据、影响及替代保护。
- mock 用于隔离明确边界；对需要真实集成或用户操作才能证明的结论，不能用 mock 结果代替。
- 计划中的假设若被新证据推翻，更新计划和测试依据，同时保留用户要求和约束。

## Computer Use 与应用验收

当目标涉及 GUI、浏览器、桌面插件、可视化结果或用户交互时，真实操作验收是必要证据的一部分。纯库或 CLI 任务没有交互要求时不必强行打开界面。

### 选择可用能力

1. 检查当前提供的浏览器、Computer Use、应用连接器或领域测试工具；需要时读取对应已安装 skill 和工具文档。
2. 使用受支持的 API、CLI 或连接器准备数据、启动程序和检查结构化输出；验证用户交互时使用实际界面或受支持的界面自动化。
3. 领域工具适合的部分交给它，例如宿主插件的加载与日志检查；通用 Computer Use 负责真实交互。只使用当前可调用且授权的能力，不假定某插件已经安装。
4. 选择测试文件、测试账号和可恢复状态。实际验收不自动授权发送消息、购买、发布或修改无关真实数据。

### 执行一次有判断力的验收

- **确认被测版本**：核对启动入口、构建产物、页面地址或插件加载结果，确认正在操作包含本次改动的版本。
- **定义场景**：写明前置条件、输入、操作与预期结果，覆盖目标中的关键用户路径及相关错误恢复路径。
- **观察再操作**：基于当前截图、可访问性树或工具返回的界面状态定位控件；按工具文档操作，不凭旧截图猜坐标或虚构成功点击。
- **核对结果**：检查可见反馈、生成文件或持久化数据及必要日志。点击了“保存”与数据确实保存是两个不同观察点。
- **留取证据**：记录实际步骤、实际结果、应用版本及必要截图或报告；截图仅支持画面中可见的事实。
- **修复再验**：发现问题后记录最小复现，修复并重跑受影响路径与相关回归。能稳定自动化的问题转成项目回归检查。
- **恢复测试状态**：清理本轮自己创建的测试数据或进程，保留复现所需材料，不干扰用户已有工作。

每项真实验收至少能回答：操作了什么、预期什么、观察到什么、证据在哪里。不要用截图存在、进程存活、页面加载或按钮可点击代替业务成功。

### 无法验收时

先尝试已授权的替代验证途径，例如浏览器工具、可重复的端到端测试、领域接口或文件内容检查，并明确它能证明的范围。

如果必要的 UI 工具、宿主软件、登录态或运行环境缺失：

- 标记具体场景未验证，保留复现步骤和所需条件。
- 继续实现与其他可执行验证；不在第一个环境障碍就放弃整个目标。
- 当该场景属于完成标准且仍无法验证时，不宣称整个目标已经通过验收。
- 只向用户提出解除实际阻塞所需的最小输入，不让用户重新制定整套测试方案。

## 最终证据

最终检查应针对交付版本和实际约束。报告命令/场景、结果、关键产物和未验证项，区分通过、失败、未运行与阻塞。相关代码改变后刷新受影响证据；已经有效通过且未受影响的检查无需机械重跑。
