# 进度、架构、历史与接手

需要建立或接续记录时读取。优先沿用项目的计划、架构和历史指南；不要在同一项目中维护两份同职责记录。初始化模板集中在 [init-files.md](init-files.md)，此处不复制模板。

## 文档分工

| 内容 | 默认位置 | 维护时机 |
|---|---|---|
| 简短导航 | AGENTS.md；CLAUDE.md 引用它 | 入口或项目关键约束变化 |
| 协作、计划、历史规则 | docs/REPO_COLLAB_GUIDE.md、PLANS_GUIDE.md、HISTORY_GUIDE.md | 协作制度变化，通常长期稳定 |
| 系统架构 | docs/ARCHITECTURE.md | 模块、接口、依赖或数据流变化 |
| 目标与进度 | docs/exec-plans/active/ 下当前计划 | 里程碑、重要方向/约束变化、阻塞、交接、交付 |
| 已交付变更摘要 | docs/histories/ 下同一任务的 history | 实质变更任务交付；长任务必要的阶段留档 |
| 暂缓处理的已证实问题 | docs/exec-plans/tech-debt-tracker.md | 确有需保留的目标外债务时 |

表中路径用于无既有约定的项目。已有 architecture、roadmap、用户指定计划或 changelog 等价文件就直接复用；不迁移文件来凑模板。简单任务可使用现有清单，简单项目架构可在 README 中简述。重要信息只存一处，其他地方引用。

## 一份计划持续推进

复杂、长期、跨模块或高风险任务应有可恢复的计划。默认从项目计划模板创建 `docs/exec-plans/active/YYYY-MM-DD-<slug>.md`；当前目标已有计划则接续它，不因新一轮调用另建。

计划应足以回答：用户要什么、边界是什么、哪些模块依赖哪些模块、各里程碑怎样验收、目前已验证什么、下一项做什么。使用具体用户能力作为里程碑，不只写“调研、实现、测试”。模块依赖可以简写，不必另建 roadmap 文件。

- 在里程碑或关键事实变化时更新状态和重要决策，不记录每次工具调用、失败重试或所有探索过程。
- 交接时把当前切片、验证缺口、阻塞和下一步写回同一计划；没有新事实不重写。
- 完成原计划目标后移入 `completed/`；修复相关导航。部分完成、预算结束和外部阻塞保留真实状态，不能作为完成归档。
- 目标内的未完成事项留在当前计划。目标外、值得后续处理的已证实问题才进入技术债清单；不要复制整个 backlog。

## 一份任务历史汇总结果

使用项目已有历史机制。采用默认骨架时，复制 `docs/histories/template.md` 到 `docs/histories/YYYY-MM/YYYYMMDD-HHmm-<slug>.md`。

同一任务跨轮次、恢复会话或多个修复切片时继续维护同一份 history。默认在实质变更任务交付时写一次；长任务确需阶段留档时更新同一文件。纯问答、研究、普通测试运行不单独建 history。

摘要保留用户诉求、主要改动、关键设计理由、必要验证结论和关键文件/计划链接即可。无需复制计划的完整进度、测试输出、diff 或操作日志。执行环境信息仅填写确实可得且有用的字段，不猜模型名称或代理身份。

## 架构与证据

架构以当前代码为准，未实现设计明确标为拟定。稳定文档只改受影响段落；产品行为变了，交付前同步受影响的使用说明。无需每轮扫描并重写所有文档。

预期结果、回归用例、夹具和可重复验收脚本保留在项目正常位置。长日志、截图与工具报告按需保存，计划或 history 只引用结论和位置。遵循项目的产物提交与脱敏规则，不复制密钥、敏感日志或隐私截图。未提交时可记录相关文件和工作区状态，不为记录而强行提交。

## 恢复与交付

新会话或上下文缺失时读取当前计划和相关架构，结合代码、工作区变更和已有证据核对事实；日常循环仅重读发生变化或当前确实需要的内容。

只重跑过期、受影响或不足以支撑判断的检查。交付前确认计划状态、必要历史和受影响说明反映最终结果；将关键验证与未解决限制讲清楚，不生成额外交付报告。

跨 Codex、Claude Code 等宿主可以共享工程事实，原生 goal、预算、权限和工具能力不能假设已自动迁移。
