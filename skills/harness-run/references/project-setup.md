# 项目检查与按需初始化

每次接手先检查实际项目；仅在需要补齐基础结构时读取本文件和 [init-files.md](init-files.md) 中相应模板。检查不生成独立报告，不每轮重做。

## 两种入口

- **新建项目**：从用户目标推导用途、模块和验收路径，建立基础文档与最小可运行骨架；首个切片落地后将拟定架构更新为实现事实。
- **现有项目**：先检查代码、启动和测试入口，再按 [existing-project.md](existing-project.md) 将有效内容整合到标准文档并清理旧体系。保留有效实现、配置和项目特有约定。新需求规划切片，既有任务恢复接续摘要后继续。

根据实际项目内容选择入口。用户给出软件目标时继续实现与验收；明确仅需初始化时完成相应基础范围。单独触发 skill 时默认完成文档与 hook 接入，说明当前接续入口。

## 判断是否就绪

查看适用的 AGENTS.md 及其他已有仓库指令、根目录与相关 docs 索引，再按需读取：

- 项目用途、当前启动/测试入口是否可确定。
- 是否有真实架构或足够说明模块、接口、依赖和数据流的等价内容。
- 长期任务是否有可接续的目标、最新用户约束、已验证版本、待验收项和下一动作。
- 是否已有计划、历史及协作约定；模板所指向的文件是否存在且有用。

核对正文中的结构、约束、进度与命令，结合源码修正空壳、占位符和失效入口。已有标准文档直接复用；其他目录中的有效内容按接入流程整理到标准位置，程序依赖随迁移更新，用户明确指定的路径按其要求处理。

| 项目现状 | 处理 |
|---|---|
| 新建或空项目 | 按下面的基础骨架实例化，建立最小运行入口并推进首个可验收切片 |
| 已有代码、文档较少 | 整合已有资料，依据代码、测试和用户目标补齐标准架构、计划与导航 |
| 已有 harness-run 基础结构 | 保留已有内容，仅补缺失且需要的文件、修复失效导航 |
| 已有其他文档结构 | 按 existing-project.md 合并内容、更新引用并清理旧体系；保留有效约束和未完成事项 |
| 基础已就绪 | 直接进入规划、实现与验证 |

调整文档维护节奏时，保留项目特有的质量门禁和协作约束，只在已授权范围内修改通用规则，不把模板当成覆盖既有指令的依据。

## 基础骨架

新建项目使用以下基础文档和模板：

```text
<project>/
├── AGENTS.md
├── README.md
├── CODEOWNERS                 # 已知真实负责人时配置
├── LICENSE                    # 已确定项目许可时生成
├── .gitattributes
├── .gitignore
└── docs/
    ├── ARCHITECTURE.md
    ├── REPO_COLLAB_GUIDE.md
    ├── PLANS_GUIDE.md
    ├── HISTORY_GUIDE.md
    ├── design/                    # 有实际专题或用户要求独立记录时创建
    ├── exec-plans/
    │   ├── README.md
    │   ├── tech-debt-tracker.md
    │   ├── active/.gitkeep
    │   ├── completed/.gitkeep
    │   └── templates/execution-plan.md
    └── histories/template.md
```

新建指令入口统一使用 AGENTS.md，后续会话由项目 hook 导航到该文件。CLAUDE.md（包括仅含 `@AGENTS.md` 的转发文件）、.editorconfig 和 .markdownlint.json 仅在用户明确要求时新增；已有文件保留其有效约定。

首次建立后按需维护，已有标准文件复用有效正文。协作指南可与既有项目约定合并。架构和计划使用上面的稳定入口；安全、可靠性、发布、界面及接口等专题放在 `docs/design/`，模板按需选取。用户指定的独立文档保留其名称与路径。

## 实例化与补齐

1. 从目录、源码、用户目标和已有元数据推断项目名、类型与约束。技术选型在授权范围内自行决定；只询问无法推断且实质影响方向的信息，不把名称、作者、团队等模板字段变成开发前置问卷。
2. 按缺口读取模板的对应章节。现有资料按接入流程合并有效内容并清理旧文件；基础配置合并适用规则，保留技术栈默认值、忽略规则、版权和所有权。
3. 实例化 README 的用途与运行入口、AGENTS 的导航、ARCHITECTURE 的模块和数据流。新项目尚无实现时标明拟定结构；首个切片落地后更新为事实。无需为了模板创建 apps/packages/infra。
4. 保留计划与历史模板供后续复用。未开始的实现不记为完成历史，模板占位可留在模板文件中，不能留在当前项目说明中。许可证和 CODEOWNERS 不明时保留已有内容或暂不生成，不填虚构身份；不阻塞其余工作。
5. 在项目 AGENTS.md 合并短导航与记录约定：恢复先读当前计划的接续摘要；用户修正及时写回约束，重要节点保存已验证版本、证据和下一动作；现行规则维护在架构或 design 专题。链接映射到实际文档，保留已有项目指令。迁移时核验新入口后再切换导航，后续会话继续遵循这些项目约定。
6. 从宿主环境或任务元数据核对真实会话工作目录，用 `--session-cwd` 传给 [项目 hook 注册](memory.md#首次注册项目-hook)。会话目录位于项目根或其子目录时，配置进入该项目的加载范围；目录不同则用宿主入口切换到目标项目，记录待确认的加载状态。使用实际安装目录与可运行的 Python；新增宿主或路径变化时再次注册。
7. 文档沿用项目语言与习惯，核对导航可达、关键内容准确、配置与当前项目相容。构建与验收入口按项目需要建立，在代码具备后实际执行；接入时区分配置注册、脚本验证和宿主真实触发的结果。

基础就绪后直接进入目标的实施循环，不把“创建完文档”当成软件目标完成，也不以“请用户继续开发”结束。用户明确只要初始化时，完成该范围即可。

## 低维护约定

AGENTS 保持短导航，指南和模板保持稳定；进度与接续沿用一份计划，交付沿用一份 history，现行规则维护在对应主题。用户修正及时保存，其他记录在重要节点更新。文档职责和维护节奏统一见 [conventions.md](conventions.md)，已有有效项目指南直接沿用。
